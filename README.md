# MLOps Platform

Kustomize-managed Kubernetes manifests for a self-hosted MLOps stack: experiment
tracking (MLflow), object storage for artifacts (MinIO), and a Jupyter notebook
environment for development — all deployed into a single `mlops` namespace and
fronted by a static dashboard at `mlops.local` linking out to each service.

## Components

`base/` is cloud-agnostic — no StorageClass or IngressClass is hardcoded there.
Those are supplied by an overlay: `overlays/local/` for k3s, and a
partially-built `overlays/eks/` for EKS (StorageClass done, Ingress not yet —
see Known gaps).

| Component | Kind | Purpose |
|---|---|---|
| `namespace` | Namespace | `mlops` namespace housing all resources |
| `mlflow-db` | StatefulSet, Service, PVC, ServiceAccount | Postgres 15 backend store for MLflow experiment/run metadata |
| `mlflow` | Deployment, Service, Ingress, ServiceAccount | MLflow tracking server (`ghcr.io/mlflow/mlflow:v2.11.3`), backed by Postgres, with artifacts stored in MinIO via S3 API |
| `minio` | StatefulSet, Service, Ingress, PVC, ServiceAccount | S3-compatible object store for MLflow run artifacts |
| `jupyter` | Deployment, Service, Ingress, PVC, ServiceAccount, Role, RoleBinding | Notebook environment (`jupyter/minimal-notebook`) for experimentation |
| `dashboard` | Deployment, Service, Ingress, ConfigMap (generated), ServiceAccount | Static nginx landing page linking out to MLflow, Jupyter, and MinIO Console |
| `config/.env.config` | ConfigMap (generated) | Non-sensitive settings — `platform-config`, generated by Kustomize's `configMapGenerator` |
| `secrets/` | Secret (generated) | Credentials — `platform-secrets`, generated locally by Kustomize's `secretGenerator`; not committed to the repo |
| `overlays/local` | StorageClass, Patches | k3s-specific `local-path-retain` StorageClass, plus Kustomize patches injecting `storageClassName`/`ingressClassName: traefik` into the base PVCs and Ingresses |
| `overlays/eks` | StorageClass, Patch (partial) | EKS-specific `ebs-gp3` StorageClass (backed by the EBS CSI driver) and a patch injecting it into the base PVCs. Validated against a throwaway `eksctl`-provisioned cluster. Ingress side (ALB controller) not started yet |

See [`docs/architecture.md`](docs/architecture.md) for a diagram of how these
pieces connect.

## Layout

```
base/                   Cloud-agnostic Kustomize base manifests (see table above)
base/config/            .env.config source for the platform-config ConfigMap
base/secrets/           .env.secrets source for the platform-secrets Secret (untracked, provided locally)
base/<component>/       Per-component manifests, each with its own kustomization.yaml —
                         namespace, mlflow-db, mlflow, minio, jupyter, dashboard.
                         Deployment/StatefulSet + Service + Ingress + PVC (where applicable)
                         are colocated in the owning component's folder.
overlays/local/         k3s overlay: local-path-retain StorageClass + patches for
                         storageClassName/ingressClassName, applied on top of base/
overlays/eks/           EKS overlay (partial): ebs-gp3 StorageClass + patch for
                         storageClassName. Ingress patch not yet written.
docs/                   Architecture diagram and other documentation
terraform-bootstrap/    One-off config creating the S3 bucket + DynamoDB table
                         used as the Terraform remote state backend below.
                         Local state, applied once, not touched again.
terraform/              Hand-rolled Terraform build of the EKS cluster itself
                         (see Provisioning EKS below) — separate from, and
                         upstream of, the Kustomize manifests in base/overlays.
```

Workloads consume `platform-config`/`platform-secrets` via `configMapKeyRef` /
`secretKeyRef` — nothing is hardcoded in the Deployment/StatefulSet specs
themselves.

## Provisioning EKS (Terraform)

`terraform/` hand-rolls the EKS cluster resource-by-resource (no
`terraform-aws-modules/eks/aws`) as a learning exercise, rather than something
`overlays/eks/` can deploy onto until this exists. It's split into a reusable
module plus a per-environment root config, mirroring the Kustomize
base/overlays split:

```
terraform/modules/eks-platform/   The actual resources — network.tf (VPC,
                                   subnets, IGW, NAT Gateway, route tables),
                                   iam.tf (cluster/node IAM roles), and more
                                   as the build progresses. No provider or
                                   backend block — inherits both from its caller.
terraform/environments/dev/       Root config: backend "s3" {}, provider
                                   config, and the module "eks_platform" block
                                   that calls the above with real values.
```

State is remote (S3 + DynamoDB lock table), created once via
`terraform-bootstrap/` and never touched again. To (re)build:

```
cd terraform/environments/dev
terraform init
terraform plan
terraform apply
```

**Status:** in progress. VPC networking and the cluster IAM role are written;
the `aws_eks_cluster` resource itself, node group, OIDC provider, IRSA, and
access entries are not yet built. Applied resources are torn down
(`terraform destroy`) between sessions to avoid idle cost (a NAT Gateway is
the only thing here that isn't free) — the cluster isn't standing 24/7 the
way the Kustomize side assumes.

## Deploying

```
kubectl apply -k overlays/local/
```

`base/` alone is intentionally incomplete (no StorageClass assigned to PVCs,
no `ingressClassName` on Ingresses) — it's always meant to be applied through
an overlay.

## Access

All services are `ClusterIP` — the only way in is through Traefik `Ingress`
on a `*.local` hostname (`NodePort` is commented out in each `service.yaml`,
left as a fallback rather than removed).

| Service | Ingress host | Purpose |
|---|---|---|
| `dashboard-service` | `mlops.local` | Landing page linking to every service below |
| `mlflow-service` | `mlflow.local` | MLflow tracking UI / API |
| `minio-service` | `minio.local` | MinIO S3 API |
| `minio-service` | `minio-console.local` | MinIO console |
| `jupyter-service` | `jupyter.local` | Jupyter notebook UI (token: `JUPYTER_TOKEN` value in the local, untracked secrets file) |

The `*.local` hosts require a Traefik ingress controller in the cluster
(`ingressClassName: traefik`) and either a DNS entry or an `/etc/hosts` entry
per host pointing at the ingress controller's address.

## RBAC

Every workload runs under its own dedicated `ServiceAccount` — none of them use
the namespace's `default` ServiceAccount, which is intentionally left unbound
so it can never become an accidental shared grant. `automountServiceAccountToken`
is `false` on all of them except `jupyter`, since none of the others make calls
to the Kubernetes API.

`jupyter`'s ServiceAccount is bound (via a `Role` + `RoleBinding`, both scoped to
the `mlops` namespace) to read-only access on `pods` — `get`/`list`/`watch` only,
nothing else. This is deliberately minimal for now; a `Role` covering `batch/v1`
Jobs will be added once notebooks start kicking off training runs as Kubernetes
Jobs.

This per-app ServiceAccount split isn't just isolation for its own sake — it
maps directly onto AWS IRSA (IAM Roles for Service Accounts), which annotates
individual ServiceAccounts to assume individual IAM roles. Keeping each
workload on its own identity now means `overlays/eks/` can add IRSA annotations
to existing ServiceAccounts rather than needing to first split workloads that
share one.

## Troubleshooting

**Ingress returns 502 Bad Gateway on every `*.local` host.** Most likely your
machine's IP has changed (DHCP lease renewal) since the `*.local` entries were
added to `/etc/hosts`. Check the two things below, in order:

1. Confirm Traefik's current address and match `/etc/hosts` to it:
   ```
   kubectl get svc -n kube-system traefik   # note the EXTERNAL-IP
   ```
   Update each `*.local` line in `/etc/hosts` to that IP.
2. If ingress still 502s after that, the IP change may have also broken k3s's
   internal pod-network routing (Traefik unable to reach the API server's
   ClusterIP) — check `kubectl logs -n kube-system -l app.kubernetes.io/name=traefik`
   for `no route to host` errors. Fix with a clean k3s restart (plain
   `systemctl restart k3s` can leave orphaned `containerd-shim` processes behind):
   ```
   sudo /usr/local/bin/k3s-killall.sh
   sudo systemctl start k3s
   ```
   Give it 30-60s, then recheck `kubectl get nodes` and `kubectl get pods -n mlops`.

## Known gaps

- `base/secrets/.env.secrets` is not committed, so `kubectl apply -k base/`
  won't work on a fresh clone until that file is created locally. There's no
  `.env.secrets.example` template yet, and no real secrets management
  (SOPS/sealed-secrets/external secrets manager) — just a gitignored
  plaintext file, which only helps for local/dev use.
- `overlays/local/kustomization.yaml` uses the deprecated `patchesStrategicMerge`
  field (not the newer unified `patches:` field) — kubectl's *bundled* kustomize
  (as used by `kubectl apply -k`) doesn't support multi-document patch files
  under `patches:`/`path:`, even though the standalone `kustomize` CLI does.
  Migrating would require splitting each multi-resource patch file into one
  file per resource; deferred for now, living with the deprecation warning.
- `overlays/eks/` is partially built: the StorageClass side (`ebs-gp3`, backed
  by the EBS CSI driver) is done and confirmed working — `kubectl apply -k
  overlays/eks/` was run against a throwaway `eksctl`-provisioned exploration
  cluster, and all app PVCs bound to real dynamically-provisioned EBS
  volumes. The Ingress side is not started — it needs the AWS Load Balancer
  Controller installed in-cluster first (EKS has no built-in Ingress
  controller, unlike k3s's bundled Traefik), which isn't done yet.
- The real EKS cluster to apply `overlays/eks/` against long-term doesn't
  exist yet — see Provisioning EKS above. The `eksctl` cluster validated
  against so far is throwaway/torn down, not the real infrastructure.
- Container images are pinned inconsistently — MinIO and Jupyter use `latest`,
  while MLflow and Postgres are pinned to specific versions.
- Ingress is HTTP-only (no TLS) and assumes a Traefik ingress controller is
  already installed in the cluster — neither the controller nor certificates
  are provisioned by this repo.
